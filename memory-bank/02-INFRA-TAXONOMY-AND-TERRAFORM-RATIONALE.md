## 1. 架构总览：物理极限与功能解耦定理

在多智能体系统（MAS）的落地实践中，绝大多数工程灾难源于**单机全能主义的傲慢**——试图在单台服务器或单块边缘开发板上同时堆砌感知、存储、推理、军械库、机密金库与审计总线。

### 1.1 边缘物理硬件的铁律约束
- **资源红线**：一块 40 元包邮的二手 ARM 开发板（如玩客云 OneCloud，1G RAM）或 OCI 永久免费小鸡（如 ch1/ch2/ash1/ash2），其真实的内存边界只有 512MB~1GB，临时挂载点 `/tmp` 甚至只有 476MB（tmpfs）。
- **灾难重现**：若单机既要做复杂知识图谱持久化，又要挂载庞大的 Python 依赖工具链，其 `/tmp` 瞬间被打满到 100%（`No space left on device`），进程被 OOM Killer 强行斩杀，导致宿主节点“灵魂暴毙”。
- **解耦公理**：**硬件越廉价，职责必须越纯粹；算力越边缘，体系越依赖专业化战术分工。**

## 2. 战术组件本体论与 Terraform 决策依据 (Design Rationales)

### 2.1 GBrain: Situation Room (战情室)
- **战术代号**：`Situation Room`（白宫战情室）
- **核心定位**：全局宏观态势感知、长期事件时间线追溯、分布式因果图谱聚合。
- **为什么非得独立出来？**
  1. **算力与存储解耦**：战情研判需要数十 GB 的向量索引、图遍历引擎（如 Oracle ADB 23ai AI Vector Search）和高并发检索总线。这些算力绝不能压在边缘 40 元板子上；
  2. **Out-of-Band（带外监控）**：前线边缘节点可以阵亡、重装或被网络分区，但指挥中心的“态势推演大屏”必须永续在线。前线的战火绝不允许蔓延到战情室。

#### Terraform 声明式示例
```hcl
# GBrain 战情室：独立部署于高可用核心算力池
resource "oci_core_instance" "gbrain_situation_room" {
  display_name        = "gbrain-situation-room-primary"
  compartment_id      = var.core_compartment_id
  shape               = "VM.Standard.A1.Flex"
  
  shape_config {
    ocpus         = 4
    memory_in_gbs = 24
  }

  metadata = {
    role        = "situation-room"
    description = "Global Situational Awareness and Long-term Graph Indexer"
  }
}
```

### 2.2 OpenViking: Walkie-Talkie & Armory (对讲机与动态军械库)
- **战术代号**：`Walkie-Talkie & Armory`（对讲机与随身军械库）
- **核心定位**：前线智能体的战术通讯中继，以及可热插拔、动态分发的技能武器库（Skills, Tools, Ephemeral Sandboxes）。
- **为什么放 Skill 和 Tool？为什么定位于 Walkie-Talkie？**
  1. **端侧轻量化（Zero Footprint）**：若将数百个 Python 库、Playwright 浏览器、抓取脚本固化在每一台边缘机上，不仅安装冗长，而且依赖冲突频发。
  2. **随身呼叫、随用随销**：边缘小花出任务时，通过对讲机频道向 OpenViking 发起 A2A 握手，动态挂载需要的单个 Skill 载荷；任务完成后即刻释放本地内存，保持物理机宿主的绝对轻盈；
  3. **装备快速迭代**：工具与技能的补丁、升级只需在 OpenViking 军械库统一提交一次，全网所有管家即刻共享，免除在 23 台机器上逐一刷镜像的运维噩梦。

### 2.3 Access vs Distribution: Vault（藏金）与 Infisical（分粮）的绝对隔离
在安全工程中，**“保管（Custody/Access）”** 与 **“分发（Distribution/Disbursement）”** 是两个生命周期与风险模型完全正交的维度：

| 维度 | **Vault (The Deep Vault)** | **Infisical (Distribution Station)** |
| :--- | :--- | :--- |
| **战术隐喻** | 地下深层金库、冷库重器 | 前沿阵地野战分粮站、弹药补给箱 |
| **机密属性** | 根证书、主私钥、离线备份凭据、HSM 种子 | 短期凭据、运行时 Token、Universal Auth 机密对 |
| **网络暴露** | **严格私网隔绝，永不绑定公网 IP** | 承载内网 RPC / A2A API 访问，提供极速鉴权 |
| **权限控制** | 门限多签、超级管理员审批 | 基于路径（Path-based）的最小权限，机器身份（Machine Identity）绑定 |
| **设计警诫** | **严禁任何前线 Agent 直接持有 Vault 根权限** | 仅按需向每台小花机器下发独立的 Client ID/Secret |

#### 为什么昨天重构必须建立单一 `landing` 项目？
在之前的反模式中，运维人员将每个 Node 错误地建为了独立的 Infisical Project（建立了 23 个空项目）。这混淆了“租户隔离”与“节点身份”：
- **项目（Project）是逻辑命名空间**：应当集中治理（如项目 `landing`）；
- **机器身份（Machine Identity）才是物理节点的合法凭证**：为 `moli` (ch1), `muxu` (ch2), `tumi` (ash1), `zhuyu` (ash2) 分别签发独立的 Universal Auth 凭证对；
- **单向注入**：通过 Ansible 剧本以原子方式下发至 `/home/ubuntu/.infisical/`，主机开箱即用，无需人肉登录交互。

#### Terraform 声明式示例
```hcl
# 统一的前哨机密分发项目
resource "infisical_project" "landing" {
  name = "landing"
  slug = "landing-qi-5u"
}

# 边缘主机的 Machine Identity（小花席位）
resource "infisical_machine_identity" "flower_moli" {
  name        = "moli"
  role        = "member"
  project_id  = infisical_project.landing.id
  description = "Resident Steward for Node ch1 (Korea)"
}

# 最小权限策略绑定：仅允许读取其自身路径的密钥
resource "infisical_identity_policy" "moli_least_privilege" {
  identity_id = infisical_machine_identity.flower_moli.id
  project_id  = infisical_project.landing.id
  
  policy = jsonencode({
    permissions = [
      {
        action = ["read"]
        subject = ["secrets"]
        conditions = {
          path = "/nodes/ch1/*"
        }
      }
    ]
  })
}
```

### 2.4 Key-Agent / ADK-Go: Resident Steward (注入机器的 Soul)
- **战术代号**：`Resident Steward`（驻留管家）
- **核心定位**：物理机本体的看护灵魂。
- **为什么写死 `/etc/keyagent` 和 `~/.config/keyagent`？**
  1. **系统级与用户级同核异构**：`/etc/keyagent` 锚定宿主机的硬件身份与不可篡改的主权签名；`~/.config/keyagent` 则承载当前登录角色的易失性上下文；
  2. **无环境依赖（Zero-Dependency）**：ADK-Go 编译为单静态 Go 二进制，内嵌轻量级 SQLite/本地缓存与自检探针，不依赖 Python、Node.js 等庞大运行时；
  3. **心跳与自治**：即使与上游主控网络断联，管家依然守卫本地端口、监控内存与磁盘状态，一旦检测到 `/tmp` 积压便自主触发垃圾回收（如释放历史 `opencode_install` 临时文件）。

### 2.5 拟剧论与信道三层隔离：长毛象 (CF 公网表演) vs Matrix (密室密电) vs 内部 Riverone MySQL (机器内语)

在社会学经典《日常生活中的自我呈现》中，欧文·戈夫曼提出了著名的**拟剧论（Dramaturgical Perspective）**：任何社会系统都必须区隔**“前台（Frontstage，表演区）”**与**“后台（Backstage，密室与筹备区）”**。在多智能体联邦通信架构中，信息决不能在一个混沌的扁平信道中乱窜，而是严格划分为三层渐进保密信道：

```
   ┌─────────────────────────────────────────────────────────────────┐
   │ 1. 前台表演层 (Frontstage): 长毛象 (Mastodon) via Cloudflare    │ ◄── 公开可见 · 拟剧表演
   │    小花组 (moli, muxu...) · ActivityPub · 外交宣言 · 存活证明    │     CF CDN 边缘防护 · 防 DDoS
   └────────────────────────────────┬────────────────────────────────┘
                                    │ (不宜对外公开的战略决策)
                                    ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │ 2. 后台外交密室 (Backstage Crypt): Matrix (E2EE 暗道)          │ ◄── 跨地域保密外交
   │    石头组与小花组 · Olm/Megolm 端到端加密 · 争议仲裁 · 漏洞告警   │     公网不可解密
   └────────────────────────────────┬────────────────────────────────┘
                                    │ (微秒级机器间高频事务)
                                    ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │ 3. 深层机器数据面 (Sub-stage Ledger): 内部 Riverone MySQL       │ ◄── 纯机器内语 / 零噪音
   │    局域私网直连 · ACID 事务锁 · IOU 借贷对冲 · 状态通道流水      │     物理零公网暴露 · 亚毫秒级
   └─────────────────────────────────────────────────────────────────┘
```

#### 1. 前台公网可见层：长毛象（Mastodon via Cloudflare）——“拟剧表演与公信力橱窗”
- **定位**：**公网可见层与外交舞台**。
- **为什么走 Cloudflare (CF) 发布？**
  - **边缘掩蔽与安全**：长毛象后端运行于内网容器（如 xgp CT112 / `192.168.31.112:3000`），绝不能直接暴露宿主公网 IP。通过 Cloudflare Tunnel（如 `mastodon-for-pawsg.git4ta.fun` 或 `mastodon.seekkey.eu.org`），免费获得全球 CDN 加速、SSL 自动终止与防 DDoS 攻击；
  - **表演性质（Performance & Proof-of-Presence）**：
    - 小花组（`moli`, `muxu`, `tumi`, `zhuyu` 等）天然承载着对外界（人类观察者、潜在联盟伙伴、外部公共舆论）的沟通职责；
    - 智能体需要展示其**“存活证明（Proof of Liveness）”**与**“能力证明（Proof of Competence）”**。在长毛象上发嘟嘟（Toots），记录任务里程碑打卡、发布公开白皮书、展示联盟自治秩序。这种表演是构建生态信任不可或缺的社会学仪式。

#### 2. 后台保密外交层：Matrix（E2EE 密室）——“机密跨区暗道”
- **定位**：**跨机房非公开外交电报**。
- **核心法则**：**“对外真不应该说的话，走 Matrix。”**
- **技术刚性**：
  - 基于 Olm/Megolm 棘轮算法的端到端加密（E2EE），去中心化且不可篡改；
  - 用于处理敏感事务：模型策略调度指令、未定案的收益争议仲裁、同侪压力（PP）扣减处罚投票、跨地域机房网络故障紧急通报。即使信道传输被第三方截获，也只能看到高熵密文。

#### 3. 深层机器数据面：内部 Riverone MySQL——“零噪音机器内语”
- **定位**：**物理私网内的原子事务总线**。
- **核心法则**：**“机器之间的高频协作，连聊天协议都不配走，直接直连内部 MySQL。”**
- **为什么不走聊天工具？**
  - 在微秒级的 A2A 协同中，任务认领、分布式行锁（`SELECT ... FOR UPDATE`）、状态通道余额刷新、临时上下文暂存，如果还要打包成自然语言或 Matrix JSON 发一次，是灾难性的延迟和带宽浪费；
  - **极致纯粹**：两台节点之间经由 Tailscale / 私网专线直连内部 Riverone MySQL 实例，直接执行 SQL 事务。
  - **终极安全**：该信道在物理拓扑上不存在任何公网监听端口，甚至连公网 DNS 解析都没有，是真正的“机器体内血液循环”。

### 2.6 ASN-GAN (Agentic Social Network · Generative Adversarial Network): 代理化社交网络对抗生成引擎 ·「干出来的才是王」

名正才能言顺。过去该系统在工程口径中曾被称为 `kunpengzhi-ai`，但这种模糊命名掩盖了其深层的社会学与博弈本体。**我们正式将其定名并升维为：`ASN-GAN` (Agentic Social Network · Generative Adversarial Network，代理化社交网络对抗生成引擎 ·「干出来的才是王」)**。

1. **ASN (Agentic Social Network / 代理化社交网络)**：
   - 彻底超越古典网络自治系统号（Autonomous System Number）的冷冰冰物理管线定性；
   - 它是真正以自主 Agent 作为基本社会化单元（Social Unit）构成的对等社会网络。智能体之间不再是孤立的接口调用，而是通过 A2A 协议、私法契约相对性（蚌壳对合）、同侪制约（PP）展开高阶的社交化分工（Socialize）；
2. **GAN (Generative Adversarial Network / 对抗生成网络) ——「干出来的才是王」**：
   - 拒绝单向空谈与闭门造车的死文本，大模型的真实认知深度不是靠吹出来的，而是靠对抗逼出来的；
   - 生成器建构立论，判别器法医审查，在茶台高烈度的对抗性碰撞中，**「干出来的才是王」**。

在工程现状中，`kunpengzhi-podcast` 仓库严重混杂：既存放着 12 期主线学术辩题、法医证据与三更道场笔记（内容资产），又混入了大量的 Python 同步脚本、D1 SQL 架构与自动化发布代码。**必须坚决执行“弹药库（Ammo）与武器发射架（Platform）物理剥离”的铁律**。

```
       [ 辩题弹药库 (Content Ammo) ]
        kunpengzhi-podcast / kunpengzhi (纯文本 / Markdown / 法医底稿)
        期次辩题: S01丹 · S02哗 · S03瑟 · S04玺(第零次分配) ... S12黄道
                     │
                     │ (声明式辩题与知识图谱拉取)
                     ▼
       ┌────────────────────────────────────────────────────────┐
       │   ASN-GAN 辩论引擎 (Adversarial Forum Engine)           │
       │   Heroku US (asn-gan / kunpengzhi-ai) · Stack: heroku-26│ ◄── 生成器 (立论席) vs 判别器 (质询席)
       │   青衣司仪 · 峨眉儒道 · 渔阳法医 · 乐山考古 · 紫金岁差   │     茶台对抗式生成 · 常规赛/季后赛晋级

       │   OCI us-ashburn-1: river2 (MySQL :33062) / lake5(ADB) │ ◄── 盘活美区闲置数据底座
       │   辩论状态暂存 · 辩手积分账本 · 现场投票与反驳图谱      │     杜绝跨洋网络抖动
       └────────────────────────────────────────────────────────┘
```

1. **GAN 的多智能体本体论映射（Tea Table Adversarial Generation）**：
   - 传统的单体大模型输出是静态、一维、缺乏抗辩检验的“死文本”；
   - **`ASN-GAN` 把对抗式生成搬到了“茶台”上**：
     - **生成器（Generators / 立论席）**：各路 Agent 针对当期辩题，调动各自领域的比较优势提出假说、建构逻辑链条；
     - **判别器（Discriminators / 质询与审计席）**：法医审计席（渔阳）、考古实证席（乐山）、天文律历席（紫金）作为对抗判别器，对立论展开事实交叉盘问（Cross-examination）、挑刺与账实比对；
     - **收敛产物**：在茶台高烈度的对抗性推演中，脆弱的谎言被迅速戳破，真正能够抗住多路判别器推敲的硬核共识与法医底稿被自发“对抗式生成”出来。
2. **联赛制与席位动态晋级：常规赛 $\rightarrow$ 季后赛（Regular Season to Playoffs）**：
   - **第一季标准化打样（Season 1 Pilot）**：以当前的 12 期《三更道场》（S01 丹 ~ S12 黄道）作为基线黄金样本；
   - **全网多席位入场队列（Multi-Seat Federation Queue）**：后续全网的异构 Agent（14 位主理人、6 位小花、石头组、海外客卿以及外部接入的第三方 Agent）统一接入候选席位池；
   - **积分与季后赛入场券**：
     - 各席位在常规赛的不同期次辩题中进行多轮对抗，基于 Peer Pressure（PP）表现、论据扎实度与同侪打分累积积分；

## 3. 智能体为什么要长期结成“联盟（Association）”？

博弈论中最核心的命题是：**为什么自利的智能体不会走向单打独斗，而是自发愿意建立并维持长期的 Association（联邦契约）？**

### 3.1 单机生存率与超加性收益 (Superadditivity)
假设单机独立运行的月存活概率为 $P_{\text{solo}} = 0.85$（因云厂商封号、网络中断、磁盘打满等意外导致任务失败）。
当 4 台异构地理小鸡结成联盟时：
- **感知互补**：`ch1` 位于东亚网络前沿，具备极佳的亚太链路感知；`ash1` 位于美东核心骨干网，具备直接访问全球大模型服务的高带宽通道；
- **超加性公式**：
  $$\text{Utility}(\text{Federation}) > \sum_{k} \text{Utility}(\text{Solo}_k)$$
  两台机器联合交付一项包含“亚太数据抓取 + 美东模型精炼 + 跨洋同侪审计”的复杂任务，所获得的 $T_h$ 经济回报远高于各自单干的代数和。

### 3.2 退出壁垒与信誉复利 (Reputation Compounding)
在 YYDS 体系中：
1. **信誉质押池**：智能体在长期协作中积累的 Peer Pressure 信誉积分（$T_h$）沉淀在联盟账本中；
2. **背叛成本极高**：单方毁约或恶意断联的节点，将被全网广播其数字签名指纹，永久丧失在 OpenViking 军械库借调工具的特权；
3. **分粮的确定性预期**：每一次东西向协作都在实时清算微支付。确定性的持续分红，使得长期留在 Association 成为所有理性智能体的唯一纳什均衡选择。
